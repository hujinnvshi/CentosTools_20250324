### 一、 系统依赖与架构特性

部分核心数据基础设施与容器化理念存在深层架构差异，直接适配调试复杂。

•   底层依赖：以 Oracle ASM 为例，其运行深度依赖操作系统内核与专属驱动，并与硬件层存储机制紧密关联，导致容器化改造风险较大。目前，公司内部 11g、12c、19c 版本的 Oracle RAC 集群均依托 ESXi 虚拟机的共享磁盘机制模拟共享存储环境。类似地，Windows Server Failover Clustering、IBM Db2 pureScale 及达梦 RAC 数据库也采用“虚拟机 + 共享存储模拟”的集群部署模式。此类依赖于底层虚拟化与共享存储机制的架构，与容器“轻量隔离、弱依赖底层硬件”的设计存在本质差异，在当前技术条件下实现容器化较为复杂。


•   商业数据库的设计特点：商业数据库产品（如腾讯 TBase、TDSQL，华为 DWS，中兴 GoldenDB，阿里 OceanBase EE 等）普遍采用高度耦合的架构设计，除核心数据存储与计算模块外，还深度集成网络通信、管理工具链及配置仓库等一系列功能。该特性与容器“单一职责”的设计理念存在一定冲突，导致其不容易被拆分为多个容器部署，且调试过程通常需原厂技术支持。此外，商业数据库普遍集成 LDAP、Kerberos、SSL 等安全机制，进一步增加了容器镜像制作与后期配置的复杂度。无论是传统多主机部署架构的产品（如 CDH、HDP、EDW），还是已提供 Kubernetes 封装的产品（如星环 TDH），均面临这个问题。


### 二、 老旧软件与特定生态的兼容性挑战

历史遗留系统及特定技术生态在容器化过程中面临显著兼容性障碍。

•   老旧软件制约：InterSystems Cache、SAP IQ、Oracle 9i 等早期软件，因缺乏适配安装包、授权机制限制、厂商停止技术支持，且对低版本系统内核存在强依赖，导致其容器化镜像制作面临较大挑战。

•   微软版本兼容差异：Windows Server 和 SQL Server 自 2016/2017 版本起才提供官方容器支持，目前我司已实现 2017-2022 版本的容器化部署；而 2000-2016 版本因缺乏官方容器方案，自行制作镜像较为复杂，尤其在 Always On 等高可用场景下存在技术瓶颈，因此仍维持基于虚拟机的部署方式。

•   混合部署现状：当前采用多版本服务通过端口隔离共部署于单机，结合 K8s 管理容器实例；集群环境则通过多虚拟机模拟实现，形成容器与虚拟机并存的混合架构。


### 三、 部署介质的获取与适配挑战

商业产品的交付形态与授权方式为容器化实施带来额外复杂度。

•   厂商交付模式限制：部分国外厂商（如 OpenText Vertica、SAP HANA2、Teradata 等）的较新版本，仅以预封装虚拟机镜像形式提供测试环境，功能受限，且正式安装包与授权需通过商务渠道获取，显著增加了部署准备的复杂度。

•   第三方镜像可用性不足：Docker Hub 等公有仓库中的相关镜像普遍版本陈旧、功能不全，与实际生产环境差异较大，导致部署时需额外协调和适配安装介质，进一步影响效率。


### 四、 建议与方案

基于当前异构并存的技术现状，建议采纳统一纳管、分类治理的演进路径。

公司目前已构建覆盖k8s、虚拟机、多主机集群及物理机的多样化部署体系，可依据实际需求灵活评估与落地，较好匹配不同场景的使用需求。然而，在资源管理方面仍存在明显短板，具体表现在监控与调度尚未实现精细化，部分非日常使用环境需保持关机状态，且依赖人工操作管控。

针对以上情况，24年年终总结确定的本年度核心目标之一便是开发集中式资源管理系统，该系统可实现物理机、虚拟机及各类服务的状态监控、开关机与服务启停的集中管控，并具备信息整合与可视化展示能力。该方案能高度适配公司现场、开发与测试等多样化场景，有效提升配置调整的灵活性与操作效率，同时降低资源能耗。
