- CPU架构因素
在国产芯片与操作系统环境下，制作容器镜像调试复杂，部署效率与资源复用率低且和实际使用环境不匹配。GoldenDB，达梦，Kingbase等服务等(特指信创场景版本)。

- 操作系统因素
针对一些历史版本软件如InterSystems Cache,SAP IQ,Oracle 9i,Oracle 10g等存在无安装包,无授权,系统版本依赖,内核兼容性调整等问题，对镜像化带来挑战。
微软软件生态问题，Windowsserver 2016和SQLSERVER  2017版本才开始提供容器化方案，公司已有部署2017,2019 版本的容器环境，对于之前2000-2016版本使用虚拟机部署
17之前版本自己制作镜像难度较大，而且在遇到特定Always On等高可用部署场景不好处理。
目前环境是多版本服务装在一起划分端口的方式来部署，集群则使用多虚拟机来实现，单机环境则使用k8s实现。

- 系统级依赖
Oracle ASM 深度依赖底层操作系统内核与驱动，与硬件高度耦合。公司现有的 11g、12c、19c RAC 集群均依托虚拟机共享磁盘机制模拟共享存储，达梦数据库亦采用类似集群模式。该架构与容器化环境难以兼容，实现困难。

- 商业产品设计因素和云原生的设计理念不同
商业产品内部组件多，容器化方案调试复杂，需要官方的支持：
商业产品在部署方案设计上通常较开源方案更为复杂，内部耦合度高，对外资料少，安装包不仅涵盖了数据存储与计算服务等核心模块，还深度集成了网络连接与通信组件、管理工具链及配置仓库等一系列功能。这些组件之间往往存在较高的内部耦合度，进一步增加了系统架构的复杂性和部署维护的难度。一般生产环境购买的正式商用数据库较多，如下
腾讯系的：TBASE，TDSQL，TBDS
Hortonworks：CDH，HDP，CDP,
新华三系列：EDW，DWS，DRDS
热普数据库的HotDB: 
星环的TDH
而且通常商业数据库会结合LDAP，Kerberos，SSL进行安全加固，对容器化过程难度进一步的提升。

- 商业策略因素：
厂家只提供了虚拟机使用,主要是商业数据库，正式授权正常渠道不易获取。
OpenText Vertica, SAP HANA2等环境新版本均为厂家封装的虚拟机，也有容器化部署的实例，不过版本较低。


目前，公司内部已建立起覆盖容器、虚拟机、多主机集群及纯物理机环境的多样化部署体系，能够依据实际使用需求进行灵活评估与部署。在资源监控与调度层面，当前尚未实现精细化管理，部分非日常使用环境暂保持关机状态，依赖人工操作，效率有待提升。
针对上述情况，本年度核心目标之一是开发一套集中式资源管理系统。该系统将实现对物理机、虚拟机及各类服务的状态监控、开关机操作、服务启停等集中管控功能，并具备信息整合与可视化展示能力。该方案高度适配公司当前多样化的现场、开发与测试场景，显著提升配置调整与修改的灵活性与操作效率。
